# שיטת העבודה של צוות Talmyeda

סקיל זה הוא **חובה**. כל סשן AI שעובד על הריפו הזה חייב לקרוא אותו לפני שהוא נוגע בקוד.
אנחנו צוות של שלוש מפתחות שעובדות על **אותם קבצים** בזמנים שונים, ולכן משמעת של תיעוד
ודחיפות תכופות היא קריטית כדי לא לדרוס עבודה אחת של השנייה.

> קישורים חשובים:
> - האפיון המלא: [`SPEC.md.DOC`](../../../SPEC.md.DOC) (מסמך Word — לחלץ טקסט לפי הצורך)
> - מצב ההתקדמות החי: [`PROGRESS.md`](../../../PROGRESS.md)

---

## 1. לפני שמתחילים לשנות — לבדוק איפה האפיון אוחז

1. **קראו את [`PROGRESS.md`](../../../PROGRESS.md)** — זהו מקור האמת למה כבר נבנה, מה בעבודה, ומה הבא בתור.
2. הריצו `git log --oneline -15` ו-`git status` כדי לראות מה נעשה לאחרונה ואם יש שינויים לא מקומיטים.
3. הצליבו מול האפיון (`SPEC.md.DOC`) — מצאו את הסעיף/מודול שאתם עומדים לעבוד עליו וודאו שהוא באמת הבא בתור ולא כבר בוצע.
4. **אל תתחילו משימה שכבר בעבודה על ידי מפתחת אחרת** (מסומן `🔧 בעבודה` ב-PROGRESS.md) אלא אם תיאמתן.

## 2. כל משימה חייבת להיות מתועדת

לפני שמתחילים משימה:
- הוסיפו/עדכנו שורה ב-[`PROGRESS.md`](../../../PROGRESS.md) עם סטטוס `🔧 בעבודה`, שם המפתחת/הסשן, ותאריך.
- אם נוח לכן, השתמשו בכלי ה-Task של הסביבה (TaskCreate/TaskUpdate) כדי לעקוב אחרי תתי-המשימות בתוך הסשן.

תיעוד משימה טוב כולל: **מה** בונים, **מאיזה סעיף באפיון** זה נובע, ו**אילו קבצים** נגעתם בהם.

## 3. בסיום משימה שעובדת — לדחוף עם תיעוד מלא

משימה נחשבת גמורה רק כאשר היא **עובדת** (הקוד מתקמפל והטסטים/הבדיקות הרלוונטיות עוברות). אז:

1. עדכנו את [`PROGRESS.md`](../../../PROGRESS.md): שנו את הסטטוס ל-`✅ הושלם`, כתבו בקצרה מה נבנה ואיך, ואילו החלטות אפיון יושמו.
2. הריצו לפני קומיט:
   ```bash
   npm run build
   npm run lint
   npm test
   ```
3. עשו קומיט **תיאורי** (ראו פורמט בסעיף 5) ואז `git push`.
4. אחרי הדחיפה — עדכנו את מה הבא בתור ב-PROGRESS.md.

## 4. כשמגיעים ל-90% מהטוקנים — דחיפה בטוחה גם באמצע משימה

ברגע שצריכת הטוקנים של הסשן מגיעה ל~**90%**, **עוצרים ודוחפים**, גם אם המשימה לא הושלמה:

1. הביאו את הקוד למצב שמתקמפל (אם אי אפשר — סמנו בבירור מה שבור).
2. עדכנו את [`PROGRESS.md`](../../../PROGRESS.md): סטטוס `⏸️ חלקי — הופסק ב-90% טוקנים`, פרטו **מה נעשה**, **איך**, **מה נשאר**, ו**מאיפה להמשיך** (קבצים, שורות, החלטות פתוחות).
3. קומיט + push. בהודעת הקומיט ציינו במפורש `[WIP - 90% token stop]`.

המטרה: אף פעם לא לאבד עבודה ולא להשאיר את הריפו במצב שמפתחת אחרת לא יכולה להמשיך ממנו.

## 5. פורמט קומיט

```
<תחום>: <תיאור קצר בזמן הווה>

- מה נעשה ולמה (הצליבו לסעיף האפיון, למשל "Section 66 auth/login")
- קבצים/מודולים מרכזיים שנגעו
- [WIP - 90% token stop]  ← רק אם זו דחיפת ביניים

Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>
```

הימנעו מ-`--no-verify`. אם hook נכשל — תקנו את הסיבה.

## 6. כללים נוספים שמקלים על עבודת צוות על אותם קבצים

- **דחפו קטן ותכוף.** עדיף כמה קומיטים קטנים על מודול אחד מאשר קומיט ענק על חצי מערכת — פחות קונפליקטים.
- **תמיד `git pull` (rebase) לפני שמתחילים ולפני push.** `git pull --rebase origin main`.
- **מודול = יחידת עבודה.** נסו לקחת משימה שמוגבלת למודול/תיקייה אחת כדי לא להתנגש עם מפתחת אחרת.
- **אל תשברו פונקציונליות קיימת** (כלל מפתח באפיון, סעיפים 2.2, 88, 104). מוסיפים — לא הורסים.
- **בטיחות רב-דיירותית (multi-tenant) לא נתונה למשא ומתן:** כל שאילתה עסקית חייבת להיות מסוננת ב-`institutionId` (אפיון סעיפים 44, 92).
- **סכימה דינמית:** `customFields` הוא תמיד מערך `[{ k, v }]` (Attribute Pattern, סעיף 35). לעולם לא אובייקט מקונן.
- **סודות לא נכנסים לקוד.** משתני סביבה בלבד (`.env`, לא בגיט).
- אם החלטה עסקית לא ברורה מהאפיון — רשמו אותה כ"החלטה פתוחה" ב-PROGRESS.md ושאלו, אל תמציאו.

---

**סדר הפעולות בכל סשן, בקצרה:** קראו PROGRESS.md → בחרו משימה → סמנו `🔧 בעבודה` → בנו → build+lint+test → עדכנו ל-`✅` → commit+push. ואם הגעתם ל-90% טוקנים — עצרו, תעדו `⏸️ חלקי`, ודחפו.
