# Docker — הסבר מורחב

(גרסה מלאה של ההסבר שניתן בצ'אט הפיתוח. תמצית קצרה נמצאת ב-[`11-glossary.md`](11-glossary.md).)

## 1. הבעיה שהמציאו את Docker כדי לפתור

לפני Docker, כשרצית להריץ אפליקציה על שרת חדש (או על מחשב של מפתחת אחרת), היית צריך:
- להתקין את השפה הנכונה (Node.js, Python, וכו') — **בגרסה המדויקת** שהאפליקציה נכתבה עבורה
- להתקין את כל הספריות התלויות
- להתקין ולהגדיר כל שירות חיצוני (מסד נתונים, cache, וכו')
- להגדיר משתני סביבה נכונים
- לקוות שמערכת ההפעלה שלך "מתנהגת" כמו זו שעליה נכתב הקוד במקור

כל שלב כזה הוא הזדמנות לבאג. התוצאה המפורסמת: **"אצלי זה עבד"** — קוד שרץ מצוין אצל מפתחת אחת ונשבר אצל השנייה, כי הסביבות שלהן שונות בפרטים קטנים (גרסת Node, גרסת ספרייה, הגדרת מערכת הפעלה וכו').

## 2. מה זה בעצם Container (מיכל)

Container הוא **תהליך מבודד** שרץ על המחשב שלך, אבל "חושב" שיש לו מערכת קבצים, רשת, ומשתני סביבה משלו — נפרדים לגמרי מהמערכת שמסביב. זה כמו "בועה" קטנה שבתוכה יש בדיוק את מה שהאפליקציה צריכה, ולא יותר.

**חשוב להבין:** container **הוא לא** מחשב וירטואלי (VM). מחשב וירטואלי מדמה **חומרה שלמה** ומריץ מערכת הפעלה מלאה משלו — כבד, איטי לעלות, צורך הרבה משאבים. Container **משתמש ב-kernel** של מערכת ההפעלה המארחת (host), ורק "מבודד" את מה שרץ בתוכו (קבצים, תהליכים, רשת). זה הופך אותו לקל משקל בהרבה — עולה תוך שניות, צורך הרבה פחות זיכרון.

```
מחשב וירטואלי:          Container:
┌─────────────┐         ┌─────────────┐
│ אפליקציה     │         │ אפליקציה     │
│ ספריות       │         │ ספריות       │
│ OS מלא       │         │ (בלי OS!)    │
├─────────────┤         ├─────────────┤
│ Hypervisor   │         │   Docker     │
├─────────────┤         ├─────────────┤
│ OS מארח      │         │   OS מארח    │
│ חומרה        │         │   חומרה      │
└─────────────┘         └─────────────┘
```

## 3. ההבדל בין Image ל-Container

זה הבלבול הכי נפוץ למתחילות:

- **Image (תמונה)** — "מתכון קפוא", קובץ סטטי שמכיל את כל מה שהאפליקציה צריכה: מערכת הקבצים הבסיסית, הקוד, הספריות, הפקודה להרצה. Image הוא **לא בהרצה** — הוא רק קובץ שמור.
- **Container** — image **שרץ בפועל**. כשאת "מריצה" image, Docker יוצר ממנו container חי — תהליך פעיל עם ה-image כבסיס.

זה בדיוק כמו ההבדל בין **מחלקה (class)** לבין **אובייקט (instance)** בתכנות מונחה עצמים: ה-image הוא ה"מחלקה", וה-container הוא "האובייקט" שנוצר ממנה. אפשר ליצור **כמה containers** מאותו image (למשל, להריץ 3 עותקים של השרת במקביל).

## 4. Dockerfile — איך בונים Image

`Dockerfile` הוא קובץ טקסט עם **הוראות שלב-אחר-שלב** לבניית ה-image. כל שורה יוצרת "**שכבה**" (layer) חדשה שנשמרת בנפרד — Docker "חכם" ומטמין (cache) שכבות שלא השתנו, כדי שבנייה חוזרת תהיה מהירה.

```dockerfile
FROM node:20                  # שכבה 1: התחל מ-image מוכן עם Node 20 מותקן
WORKDIR /app                  # שכבה 2: תיקיית עבודה בתוך ה-container
COPY package*.json ./         # שכבה 3: העתק את קבצי התלויות
RUN npm install                # שכבה 4: התקן dependencies
COPY . .                      # שכבה 5: העתק את שאר הקוד
RUN npm run build              # שכבה 6: קמפל את הפרויקט
EXPOSE 3000                    # מסמן שהאפליקציה מאזינה בפורט 3000
CMD ["npm", "run", "start:prod"]  # הפקודה שרצה כשה-container מתחיל
```

**נקודה חשובה על סדר השורות:** שמים `COPY package*.json` ו-`npm install` **לפני** `COPY . .` (שאר הקוד) בכוונה. אם הקוד משתנה (מה שקורה כל הזמן) אבל ה-package.json לא השתנה, Docker ישתמש ב-cache של שכבת ה-`npm install` ולא יתקין את כל הספריות מחדש בכל build — חוסך המון זמן.

## 5. איך זה נשמר בפועל (Registry)

אחרי שבונים image, אפשר "לדחוף" (`docker push`) אותו ל-**registry** — מאגר מרכזי (הכי מוכר: Docker Hub, אבל גם GitHub Container Registry, AWS ECR וכו'). משם, כל שרת/מחשב יכול "למשוך" (`docker pull`) את אותו image המדויק ולהריץ אותו. זו הדרך שבה קוד "עובר" מהמחשב שלך לשרת הפרודקשן — לא מעתיקים קבצים ידנית, מעבירים image שלם ומוכן.

## 6. Volumes — פתרון לבעיה של "container הוא זמני"

יש כלל חשוב: כל מה שנכתב **בתוך** container נמחק כשהוא נסגר (container הוא "בן חלוף" במהותו — stateless). זו בעיה חמורה למסד נתונים כמו MongoDB — לא רוצים שהדאטה תיעלם בכל פעם שמפעילים מחדש!

הפתרון: **volume** — תיקייה על המחשב המארח (host) ש"מוצמדת" לתוך ה-container. כל מה שה-container כותב לנתיב הזה, בפועל נשמר על המחשב האמיתי, לא נעלם. בדוגמה של MongoDB:
```yaml
volumes:
  - mongo_data:/data/db
```
`/data/db` הוא איפה MongoDB שומר את הקבצים שלו **בתוך** ה-container; `mongo_data` הוא volume אמיתי על המחשב, שנשאר קיים גם אם מוחקים ומרימים מחדש את ה-container.

## 7. docker-compose — הרצת כמה containers ביחד

אפליקציה אמיתית כמעט אף פעם לא מורכבת מ-container בודד. אצלנו: יש **שרת NestJS** ו**MongoDB** — שני containers נפרדים שצריכים "לדבר" ביניהם. `docker-compose.yml` מתאר את **כל המערכת** במקום אחד:

```yaml
services:
  backend:
    build: .                          # בנה מה-Dockerfile שלנו
    ports:
      - "3000:3000"                   # מפה פורט 3000 במחשב לפורט 3000 ב-container
    environment:
      - MONGODB_URI=mongodb://mongo:27017/talmyeda
    depends_on:
      - mongo                         # תחכה שה-Mongo יעלה קודם

  mongo:
    image: mongo:7                    # image מוכן מ-Docker Hub, לא בונים בעצמנו
    ports:
      - "27017:27017"
    volumes:
      - mongo_data:/data/db

volumes:
  mongo_data:
```

**נקודה מעניינת:** ב-`MONGODB_URI`, כתוב `mongo:27017` ולא `localhost:27017`. זה כי Docker Compose יוצר **רשת פנימית** אוטומטית שבה כל service יכול "לקרוא" לשירות אחר **בשם שלו** (`mongo`) כאילו זה hostname רגיל — קסם קטן שחוסך הגדרת רשת ידנית.

עם הקובץ הזה, פקודה **אחת**:
```bash
docker compose up
```
מרימה גם את ה-Mongo וגם את השרת, מחוברים נכון, בלי שאף אחת בצוות תצטרך להתקין MongoDB בעצמה על המחשב שלה.

## 8. למה זה חשוב במיוחד בפרויקט הזה

זה ממש רלוונטי לצוות של שלוש מפתחות על אותו קוד:
- **סביבת פיתוח אחידה** — כולן מריצות בדיוק אותה גרסת Node/Mongo, בלי קשר למה שמותקן להן במחשב
- **onboarding מהיר** — מפתחת חדשה לא צריכה להתקין כלום חוץ מ-Docker עצמו כדי להריץ הכל
- **מוכנות לפרודקשן** — אותו image שרץ בפיתוח יכול לרוץ בדיוק אותו דבר בשרת אמיתי (עקרון "build once, run anywhere")
- **בדיקות אמיתיות מול DB** — כרגע (ראו PROGRESS.md) אין MongoDB זמין להרצה בסביבת הפיתוח בה נכתב הקוד. עם `docker-compose.yml` מוכן, כל מפתחת (וגם CI/CD בעתיד) יכולים להרים MongoDB אמיתי תוך שניות ולהריץ טסטים אמיתיים — זה בדיוק מה שהאפיון דורש בסעיף 101 ("Docker Support... The system should be easy to run locally").

## 9. פקודות בסיסיות שכדאי להכיר

| פקודה | מה היא עושה |
|---|---|
| `docker build -t talmyeda-backend .` | בונה image מה-Dockerfile |
| `docker compose up` | מריץ את כל השירותים מ-docker-compose.yml |
| `docker compose up -d` | אותו דבר, אבל ברקע (detached) |
| `docker compose down` | עוצר וממחזר את כל ה-containers |
| `docker ps` | מציג containers שרצים כרגע |
| `docker logs <container>` | מציג את הלוגים של container ספציפי |
